How the pricing model works

A technical brief for the HouseAccount team. The system takes a home-service job described in plain English and returns a price range (low / likely / high) plus a confidence score — and gets more accurate as real job outcomes come back.

The job, end to end

job description + category + zip │ ① Claude Haiku reads the text ──► structured scope │ (labor-only? area? #tasks? complexity?) ② Build feature vector ──► scope + urgency + local income + category │ ③ 3 XGBoost models predict ──► low (5%) · likely (50%) · high (95%) │ ④ Confidence score + out-of-range check │ ⑤ Store the estimate ──► return range + confidence to the app

1 · Reading the job (the AI part)

The hard part of pricing is that a "Handyman" job can be a $90 faucet swap or a $900 multi-task day. We use Claude Haiku to read the free-text description and pull out structured signals — is it labor-only, is there an area measurement, how many tasks, how complex — via a strict tool-call so the output is always clean JSON.

Example: a request says "just labor, I have my own parts." Haiku flags labor_only = true, which tells the model to drop the materials portion of the price — the single biggest correction it makes.

Calls are cached (same description → no second call), and wrapped in a circuit breaker with one retry: if Haiku is slow or down, we fall back to safe defaults and still return a price rather than failing.

2 · The features

The scope signals are combined with: deadline urgency, the local median income (looked up from the zip code), the customer's original estimate (or the category's typical price if none), and a one-hot flag for the service category (18 supported).

3 · The model

Three XGBoost quantile-regression models run together — one predicts the 5th percentile (low), one the 50th (the likely price), one the 95th (high). That's how we get a real range, not just a single number, with a calibrated 90% interval.

Trained on ~410 real historical jobs and validated with 5-fold cross-validation. Blended error is around 11% MAPE (average % off the final price), beating the old original-estimate baseline — with the biggest wins on the messy categories (Handyman dropped from ~48% to ~37% error). Two refinements: high-variance categories get slightly wider ranges so the true price actually lands inside, and categories the model already prices well are left on their trusted baseline.

4 · Knowing when it's unsure

Every estimate gets a confidence score from how wide its range is. It's deliberately capped low for big-ticket jobs (>$5,000), very wide ranges, and out-of-distribution inputs — e.g. a category or job size the model hasn't really seen. Those surface in the app as a "Rough" estimate instead of a confident one, so we never present a shaky number as solid.

5 · It learns over time

When a job closes, the real final price is sent back. The system tracks rolling 90-day accuracy (overall and per category), and:

  1. Auto-retrains once enough new outcomes accumulate (default: 20).
  2. Watches for drift — if 30-day error crosses a threshold, it alerts.
  3. Exposes everything as live metrics (the dashboard on the previous page).

Why these tools & models

The pricing pipeline is a deliberate split — a language model for understanding, a statistical model for the number — and each piece was chosen for a specific reason:

An LLM reads the job; a trained model sets the price. A language model is excellent at understanding messy free-text, but it isn't calibrated for numeric prediction, can't give a statistically grounded range, and can't learn from real outcomes. A trained model is the reverse. So each does only what it's best at.
Instead of: asking the LLM to name a price directly — unreliable numbers, no real confidence range, no feedback loop.
XGBoost (gradient-boosted trees) for the prediction. With only a few hundred labeled jobs and a mix of signals, boosted trees are the sweet spot: they capture interactions (labor-only on a Handyman job behaves differently than on an HVAC job), need little tuning, and resist overfitting on small data.
Instead of: deep learning (needs far more data, overkill here) or plain linear regression (misses those interactions).
Quantile regression — a real range, not one number. Three models predict the low, likely, and high price, giving a calibrated 90% range. Pricing is genuinely uncertain; a range plus a confidence score is more honest, and more useful, than a single figure that's quietly wrong.
Claude Haiku specifically. Scope extraction is a narrow, well-defined task that sits on the live request path, so speed and cost matter. Haiku is fast and inexpensive, and forcing a structured tool-call guarantees clean data every time. A larger model would add latency and cost with no real accuracy gain here.
Instead of: a frontier-size model — slower and pricier for no benefit on a constrained extraction task.
Trust the existing estimate where it's already good. For categories the original estimate already prices well, we keep it and let the model override only the hard categories where it measurably beats the baseline — maximizing accuracy while minimizing the risk of making a good estimate worse.

Architecture

Two small services, one repo, both deployed on Railway straight from GitHub:

Browser ──► pricing-api (Rails) ──private network──► pricing-ml (Python) public UI + API proxy the model + Claude Haiku SQLite of estimates & outcomes

The Rails app is the public face (the demo UI and booking); the Python service does all the model work. They talk over Railway's private network with a shared secret, so the model isn't directly exposed. This documentation site is served separately from GitHub Pages and reads the live metrics over a public read-only endpoint.
